1. 你在项目中设计的三级 Cache 分层结构具体是怎样的？各层级的容量、相联度等参数是如何确定的？为什么选择这样的参数配置？

   答：L1采用四路组相连，四个单端口SRAM BANK；L2和L3采用八路组相联，八个单端口SRAM BANK；

​	原因：给出的要求是三级cache的总量是128kb，第一级的cache面积乘以8，第二级的cache面试乘以2，第	三级乘以1。综合容量以及延迟，考虑L1 8KB，L2 16KB，L3 32KB。由于SRAM只支持单端口操作，采用全	相联的话，每一行cacheline都需要比较器，硬件消耗大，直接映射的话，由于L1 cache的容量比较小，会频	繁cache line冲突。

​	高相联度需要更复杂的比较电路，会增加延迟和功耗。L1 作为最靠近 CPU 的 Cache，对延迟极其敏感，因	此采用较低的相联度（四路）；而 L2/L3 对延迟的敏感度低于命中率，因此可承受更高相联度的硬件开销。

2. 你提到在 L1 Cache 前增设了 Instruction Buffer，能详细说说这个 Buffer 的大小是如何设计的吗？

   答：设计的LOAD STORE QUEUE的深度是64，环形 LSQ 本质是一个循环缓冲区（Circular Buffer），通过两个指针管理队列状态：tail 指针：指向队列中 “下一个待插入操作” 的位置，新发射的 Load/Store 指令会被写入 tail 指向的地址。head 指针：指向队列中 “最早发射且未完成” 的操作，当该操作完成（如内存访问结束、地址计算完成），head 递增，释放队列空间。

3. non_blocking的结构是如何实现的，？

   答：每一级的MSHR的容量都是上一级MSHR和Write back buffer容量的总和，因此每一级向下发送的指令，下一级定能够接收。相应的，因为每一级存在MSHR，因此下一级向上一级进行响应时，上一级也一定能接收响应，因此实现了non_blocking结构。

   L1 MSHR深度是32，write back buffer深度是16；

   L1 MSHR深度是48，write back buffer深度是16；

   L1 MSHR深度是64，write back buffer深度是16；

4. 多路组相联 Cache 采用串行访问 Tag SRAM 和 Data SRAM，构建四级流水线来优化 LOAD 指令延迟，能讲解一下这个四级流水线的具体 stages 吗？相比并行访问，串行访问在时序和功耗上有什么优缺点？

​	答：

​	四级流水线的核心是将 “地址解析→Tag 查找→命中判断→数据读取” 的串行过程拆解为流水级，每级在一个	时钟周期内完成，从而降低单周期的关键路径延迟。

​	**Stage 1：地址解析与组索引计算**

- **核心操作**：
       接收指令物理地址，解析出 Cache 的**组索引（Index）** 和**标记位（Tag）**。
  - 组索引用于定位该地址属于 Cache 的哪个组（组相联中，每组包含 N 个路，每个路对应一个 Tag 和 Data 块）；
  - 标记位用于后续与该组内所有路的 Tag 进行比对，判断是否命中。
- **硬件动作**：
       地址线信号稳定后，通过组合逻辑计算组索引的二进制编码，同时暂存 Tag 值到寄存器（为下一级的 Tag 比对做准备）。
- **关键目标**：完成地址的拆分，为下一级的 Tag SRAM 访问提供索引。

​	**Stage 2：Tag SRAM 访问与 Tag 读出**

- **核心操作**：
       根据 Stage 1 计算的组索引，访问该组对应的**所有 N 路 Tag SRAM**（组相联中，每组的 N 个路共享同一组索引，需同时读出所有路的 Tag 进行比对）。
- **硬件动作**：
       组索引信号输入 Tag SRAM 的地址端口，经过     SRAM 的访问延迟（如字线激活、位线感应），将该组内 N 个路的 Tag 值和状态位（有效位等）读出到寄存器中。
- **关键目标**：从 Tag SRAM 中获取当前组内所有可能匹配的 Tag，为下一级的命中判断提供数据。

**	Stage 3：Tag 比对与命中判断**

- **核心操作**：
       将 Stage 1 暂存的 Tag 值与 Stage 2 读出的 N 个路的 Tag 值进行**并行比对**，同时检查对应路的有效位（确保数据有效）。
- **硬件动作**：
  - 用 N 个比较器（Comparator）同时对比 Tag 值，输出每个路的匹配信号（1 表示匹配，0 表示不匹配）；
  - 结合有效位，生成 “命中信号（Hit）” 和 “命中路索引（Hit Way）”—— 即哪一路（若命中）的 Tag 匹配且有效。
- **关键目标**：确定当前 Load 指令是否命中 Cache，以及命中的具体路，为下一级的 Data SRAM 访问提供索引。

​	**Stage 4：Data SRAM 访问与数据输出（Data SRAM Access & Data Output）**

- **核心操作**：
       根据 Stage 3 确定的 “命中路索引” 和 Stage 1 的组索引，访问该组内命中路的**Data SRAM**，读出对应的数据块，并根据 Load 指令的字节偏移（Offset）提取所需的字节 / 半字 / 字（即最终要写入寄存器的数据）。
- **硬件动作**：
  - 组索引和命中路索引共同作为 Data SRAM 的地址，激活对应的数据存储单元；
  - 数据读出后，通过字节选择器（Byte Mux）根据 Offset 截取有效数据，输出到寄存器文件或流水线后续阶段。
- **关键目标**：完成数据的读取和整理，为 Load 指令的结果提交做准备。

5. 流水线进行的时候，如何确保不会把该行替换掉？

   答：通过**硬件标记跟踪**和**替换策略互斥机制**来实现保护。核心思路是：对处于流水线处理过程中的 Cache 行设置 “锁定” 或 “活跃” 标记，阻止替换逻辑选择这些行作为替换候选，直到流水线操作完成。

6. MSHR、Victim Buffer、PLRU 这些模块在整个 Cache 系统中分别扮演什么角色？

   答：

   MSHR：监听指令miss的处理过程，协调下一级存储（如 L2、内存）的数据加载，避免缺失处理阻塞流水线。与流水线交互：MSHR 会向流水线反馈 “缺失未完成” 状态，暂停等待该数据的指令，同时允许无关指令继续执行（乱序处理器中），直到数据返回后唤醒阻塞的指令。
   Victim write Buffer：临时存储被 Cache 替换出去的 “脏行”（Dirty Line，即数据已修改但未写回下一级存储的 Cache 行），避免替换操作阻塞当前指令执行。并且支持命中，再次命中通过MSHR写回。

   PLRU（Pseudo-LRU，伪最近最少使用）：Cache 替换策略的一种实现方式，用于在 Cache 组内选择 “最不常用” 的行作为替换候选，平衡替换效率与硬件复杂度。
   具体功能：跟踪访问历史：在多路组相联 Cache 中（如 8 路组相联），PLRU 通过二叉树结构的状态位记录各 Cache 行的访问顺序（而非完整的 LRU 队列）。例如，8 路组相联需要 7 个状态位（2^3-1），每个位表示 “某一子树中的行是否比另一子树更久未被访问”。

8. 在设计过程中，有没有遇到过时序违例或者功能错误的问题？如果有，你是如何定位并解决这些问题的？

   #### 高频模块的 Setup 违例（某 CPU 接口控制器）

   - **现象**：在 1GHz 目标频率下，STA 报告某条数据通路的 setup slack 为 - 0.2ns（不满足要求），涉及多级组合逻辑（地址解码→数据选择→CRC 计算）。

   - 定位过程

     用 PrimeTime 生成时序报告，查看关键路径（Critical Path）：发现地址解码模块的组合译码逻辑（支持多种地址模式）存在多级嵌套的条件判断（if-else 链），导致组合延迟达 0.8ns，远超目标周期（1ns）。

   - 解决方法

     1. **逻辑优化**：将串行译码的 if-else 链重构为并行查找表，用组合逻辑替换条件判断，将译码延迟从 0.8ns 降至 0.4ns。
     2. **流水线拆分**：在 CRC 计算前插入插入一级寄存器，将单周期内的组合逻辑延迟延迟拆分为两级流水线，每路径总路径延迟分摊到两个周期。
     3. **物理优化**：通过 Floorplan 调整模块位置，减少关键路径的布线长度，线延迟降至 0.1ns。
        优化后，setup slack 变为 + 0.3ns，满足时序要求。

   #### 案例 2：跨时钟域跨时钟的 Hold 时序违例（异步 FIFO 接口）

   - **现象**：跨时钟域数据跨时钟（100MHz→200MHz）传输时，后仿真发现偶发数据错误，STA 报告跨时钟域路径 hold slack 为 - 0.1ns。

   - 定位过程

     ​	检查异步 FIFO 的同步器设计：发现数据总线（32 位）未采用 “格雷码编码”，直接用两级寄存器同	步，导致多 bit 同时跳变时，同步器输出 metastable（亚稳态）的概率升高。

     1. 分析时序报告：快时钟域（200MHz）采样慢时钟域（100MHz）数据时，由于数据保持时间不足，采样到不稳定状态。

   - 解决方法

     1. **同步器优化**：将数据总线拆分为 “地址 + 数据”，地址采用格雷码编码（每次只跳变 1bit），数据通过异步 FIFO 缓冲，避免多 bit 同时跨时钟域。
     2. **增加 hold buffer**：在快时钟域的采样寄存器前插入一级缓冲寄存器，延长数据的保持时间，使 hold slack 恢复至 + 0.2ns。

##### 替换策略更新的时机

场景 1：Cache 命中（Hit）时 —— 更新 PLRU 状态，标记 “最近使用”

场景 2：Cache 缺失（Miss）且需替换时 —— 淘汰 PLRU 块 + 初始化新块状态

场景3： Cache 未满时，**无需触发 PLRU 替换**，仅更新 PLRU 状态位（标记新块为 “最近使用”）。
